## ADR-001. Стек задан заказчиком

**Статус:** принято · **Дата:** 2026-09-14

**Контекст.** Finanse plus передали список технологий их боевого проекта: TypeScript 5.7, React 19, Next.js 16 с App Router, Tailwind CSS 3 + CSS Modules, PostCSS и Autoprefixer, pnpm 10.

**Решение.** Следуем списку буквально, без «улучшений». Версии в `package.json` пинятся точно, без диапазонов `^`.

**Причина.** Тестовое рассматривается как вход в постоянное сотрудничество. Код читают как образец того, каким он будет в их репозитории. Отклонение от заданного стека — первое, что заметят на ревью, и объяснять придётся не технику, а зачем вы проигнорировали требование.

**Следствия.** Некоторые современные удобства недоступны — см. ADR-004. Это цена совместимости, и она осознанная.

## ADR-002. UI-библиотека: заимствуем поведение, а не внешний вид

**Статус:** принято · **Дата:** 2026-09-14

**Контекст.** Писать с нуля цветовой пикер, поповер с позиционированием, селект с клавиатурной навигацией — потерянное время. При этом задание дословно требует «предложить собственную визуальную реализацию».

**Рассмотренные варианты.**

| Вариант | Почему отклонён или принят |
|---|---|
| MUI / Ant Design / Chakra / Mantine | **Отклонено.** Экран получит узнаваемый вид этой библиотеки. Проверяющий увидит визуальное решение её авторов, а не наше — то есть именно то, что оценивается, окажется чужим |
| shadcn/ui | **Отклонено.** Код копируется в репозиторий и его можно перекрасить, но «дефолтный shadcn» узнаётся с первого взгляда, а перекрашивать его под нашу сетку дольше, чем собрать 8 контролов на голом Radix |
| Base UI (`@base-ui-components/react`) | **Отклонено.** На момент решения всё ещё `1.0.0-rc.0` от декабря 2025. Для тестового брать RC не стоит |
| `radix-ui` + `react-colorful` | **Принято** |

**Решение.** Headless-слой: `radix-ui` (unified, 1.6.7) — клавиатурная навигация, фокус-трапы, ARIA и позиционирование без единого навязанного стиля. `react-colorful` (5.8.1, 2.8 КБ, ноль зависимостей) закрывает пикер. Иконки — `lucide-react`.

**Причина.** Скучную и легко ломающуюся часть — доступность и обработку краевых случаев — отдаём библиотеке. Внешний вид остаётся полностью нашим, и именно он идёт на оценку. Там, где Radix не даёт поведения сверх того, что уже есть у нативного элемента (кнопка с `onClick`, текстовый `<input>`) — используется нативный элемент, а не обёртка ради обёртки.

**Следствия.** Семь примитивов реально используются и делают реальную работу: `Switch` (тумблеры, `role="switch"` + `aria-checked`), `Select` (клавиатурный listbox), `Popover` (позиционирование и фокус-трап попапа цветового пикера), `Tabs` (рельс разделов + мобильный переключатель, `role="tablist"` со стрелками), `ToggleGroup` (сегментированные контролы), `AlertDialog` (подтверждение сброса — фокус-трап, `Escape`, затемнение), `Tooltip` (подписи к icon-only кнопкам — Undo/Redo/тема/зум/печать/рельс — доступные с клавиатуры, в отличие от нативного `title`). Ни один из них не требует ручной реализации фокуса или ARIA.

`Slider` и `Accordion` из первоначального списка (см. черновик в `docs/PLAN.md`) не использованы: зум сделан пошаговыми кнопками, а не перетаскиванием — раскладка в `UI-SPEC.md` буквально рисует `[− 100% +]` (минус/процент/плюс), а не трек с ползунком, и это не решение постфактум, а следование уже нарисованной раскладке. Раскрывающихся секций в финальном UI-SPEC нет — там фиксированные разделы с разделителями-линиями, а не аккордеон.

*Ретроспектива.* При первом проходе `Tooltip` был по ошибке молча вычеркнут из этого списка вместе с `Slider`/`Accordion` — то есть документация подгонялась под уже написанный код, а не код доводился до того, что документация обещала. На самом деле у icon-only кнопок не было видимой подсказки при наведении вообще (только `aria-label` для скринридера и местами нативный `title`, не фокусируемый с клавиатуры) — реальный, а не мнимый пробел. Исправлено реализацией `components/ui/Tooltip.tsx`, а не правкой текста.

## ADR-003. Jotai вместо React Context

**Статус:** принято · **Дата:** 2026-09-14

**Контекст.** Одно состояние настроек шаблона, которое читают и панель настроек, и документ-предпросмотр, и верхняя панель.

**Рассмотренные варианты.**

- **React Context + useReducer** — ноль зависимостей, но любое изменение значения перерисовывает всех потребителей.
- **Zustand** — селекторы решают проблему ре-рендеров, но состояние остаётся одним объектом.
- **Jotai** — принято.

**Решение.** Jotai **2.20.3**, не 3.x.

**Причина — главная.** Точечные ре-рендеры. С Context движение ползунка цвета перерисовывает панель, документ и топбар целиком — десятки обновлений в секунду на перетаскивании, и лаг будет заметен именно в предпросмотре. С атомами перерисовывается только подписанный лист. Для экрана, вся суть которого в мгновенном отклике, это профильный выигрыш.

**Причина — дополнительная.** Три реально асинхронных места: загрузка логотипа (`File` → `FileReader` → data URL), SSR-безопасная гидрация черновика из `localStorage`, дебаунс записи. `atomWithStorage` и async-атомы закрывают их чисто.

**Почему версия 2, а не 3.** Jotai 3.0.0 вышел 08.09.2026, за шесть дней до решения. `jotai-history` объявляет peer `jotai >= 2.9.0` — формально ставится, но под v3 не тестировался. Для тестового задания риск не оправдан.

**Почему без `jotai-optics`.** Он тянет `optics-ts`, не обновлявшийся с июля 2023, а сам не обновлялся с мая 2024. Нужные линзы пишутся в ~25 строк на голом `atom()`.

**Следствия.** Возникает противоречие между атомарностью и undo/redo: история работает со снимками всего состояния, а гранулярность — со множеством независимых атомов. Решается одним базовым атомом и производными линзами:

```ts
export const settingsAtom = atomWithStorage<TemplateSettings>(STORAGE_KEY, DEFAULTS);

function fieldOf<S, K extends keyof S>(parent: Writable<S>, key: K): Writable<S[K]> {
  return atom(
    (get) => get(parent)[key],
    (get, set, value: S[K]) => set(parent, { ...get(parent), [key]: value } as S),
  );
}

export const primaryColorAtom = fieldOf(brandingAtom, 'primaryColor');
```

Компонент подписан на свою линзу и не знает об остальных настройках; `jotai-history` версионирует только базовый атом.

**Подводный камень.** Гидрация из `localStorage` происходит в эффекте и попадает в историю отдельным шагом — первое Undo откатило бы черновик к дефолтам. Лечится сбросом истории после гидрации (`set(historyAtom, RESET)`).

## ADR-004. Tailwind 3, а не 4

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Заказчик указал Tailwind CSS 3. На момент решения актуальна ветка 4.3.x, последняя в третьей ветке — 3.4.19 от декабря 2025.

**Решение.** Tailwind 3.4.19. Не мигрировать.

**Причина.** Требование заказчика, и оно обосновано:

1. **Совместимость с CSS Modules.** В v4 каждый CSS-файл обрабатывается изолированно, поэтому `@apply` и обращения к токенам внутри модуля падают с `Cannot apply unknown utility class`, пока в начало файла не добавлен `@reference "../app/globals.css"`. При стеке «Tailwind + CSS Modules» это постоянное трение. В v3 работает без оговорок.
2. **Поддержка браузеров.** v4 требует Safari 16.4+, Chrome 111+, Firefox 128+ (`@property`, `color-mix()`, cascade layers). Для SaaS бухучёта с корпоративными клиентами на старых машинах это может быть неприемлемо.
3. **Autoprefixer в стеке.** Он нужен именно v3; в v4 его роль забирает Lightning CSS.

**Честная оговорка.** Для схемы «токены как CSS-переменные» v4 был бы чуть удобнее: `@theme` генерирует переменные автоматически, а в v3 нужен ручной мостик `colors: { surface: 'var(--surface)' }`. Это десять строк конфига один раз — на фоне пункта 1 несущественно.

## ADR-005. Граница между Tailwind и CSS Modules

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** В стеке присутствуют оба подхода. Смешивать их без правила — верный способ получить кашу.

**Решение.**

**Tailwind** — всё, что является композицией токенов: отступы, сетка, флекс, типографическая шкала, цвета интерфейса, состояния `hover` / `focus-visible` / `disabled`, адаптив, тёмная тема. Около 85 % разметки.

**CSS Module** — когда строка классов переваливает за ~12 утилит или нужен селектор, которого нет в разметке:

| Случай | Почему модуль |
|---|---|
| `InvoicePaper.module.css` | Документ живёт на CSS-переменных, которые задаёт пользователь (`--tpl-primary`, `--tpl-font`, `--tpl-density`). Утилитами это не выражается в принципе |
| `PreviewCanvas.module.css` | Многослойная тень бумаги, трансформация зума |
| `ColorField.module.css` | Переопределение внутренних классов `react-colorful` — стороннюю разметку утилитами не покрасить |
| `print.module.css` | `@media print`, `@page` |
| `Toggle.module.css` | Анимация ползунка по `[data-state]` от Radix |

Модуль лежит рядом со своим компонентом (`Toggle.tsx` + `Toggle.module.css`), а не в общей папке стилей — так проще удалять компонент целиком.

**Токены объявляются один раз** в `app/globals.css` как CSS custom properties и пробрасываются в утилиты через `theme.extend` в `tailwind.config.ts`, чтобы оба подхода читали одни и те же значения.

## ADR-006. Системные шрифты вместо next/font

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Изначально планировался Inter через `next/font/google`.

**Решение.** Системный стек: `-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, ...`.

**Причина.** Сборка перестаёт зависеть от доступности внешней сети — в изолированных окружениях и в CI без исходящего интернета `next/font/google` падает на этапе билда. Плюс ноль сетевых запросов у пользователя и ноль сдвига макета при загрузке шрифта.

**Следствия.** На macOS и Windows системный стек выглядит ровно, различия между платформами есть, но в рамках инструментального интерфейса они незаметны.

## ADR-007. Деньги в целых минорных единицах

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Предметная область — бухгалтерский учёт.

**Решение.** Все денежные величины хранятся целыми числами в минорных единицах (гроши, центы). Округление — один раз, при выводе, банковским способом. Форматирование через `Intl.NumberFormat`.

**Причина.** `0.1 + 0.2 !== 0.3` в double, и на длинных таблицах позиций это даёт расхождение в итогах. Для платформы учёта это не перестраховка, а базовая корректность — и одна из немногих деталей, по которой профильный заказчик сразу поймёт уровень.

**Следствия.** Итоги пересчитываются от того, какие блоки включены: скрытие Discount или Taxes убирает суммы из Total и Balance Due, а не просто прячет строку. Документ обязан сходиться в любой конфигурации.

## ADR-008. Нейтральная палитра интерфейса

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** В референсе интерфейс ярко-синий, и этот же синий стоит в предпросмотре документа как выбранный пользователем цвет.

**Решение.** Интерфейс нейтрально-графитовый, без собственного цветного акцента. Активные состояния — цвет чернил. Кольцо фокуса тоже нейтральное, не синее.

**Причина.** На этом экране пользователь выбирает цвета своего бренда. Цветной интерфейс конкурирует с настраиваемым документом и искажает восприятие выбранного оттенка — выбрать цвет на синем фоне и увидеть его же на белой бумаге это разные ощущения. Единственное цветное пятно на экране должно быть самим счётом.

**Следствия.** Документ остаётся белым в обеих темах интерфейса: это лист бумаги, а не поверхность приложения.

## ADR-009. Тестовый стек: Vitest + React Testing Library

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Ни в стеке заказчика, ни в `PLAN.md` изначально не было тестового раннера — пробел, вскрытый на ревью плана. Для платформы бухучёта покрытие тестами арифметики (расчёт итогов) и линз состояния значимо, а не «для галочки».

**Рассмотренные варианты.**

| Вариант | Почему отклонён или принят |
|---|---|
| Jest + RTL | Дольше настраивается под Next.js 16 App Router и ESM-модули (`react-colorful`, `radix-ui`) |
| Только юнит-тесты на чистых функциях, без RTL | Не покрывает поведение компонентов (`Toggle`, `ColorField`), а именно там легко сломать доступность при рефакторинге |
| Vitest + Playwright e2e | Избыточно для объёма задания — e2e не добавляет уверенности сверх юнит- и компонентных тестов при таком размере экрана |
| **Vitest + React Testing Library** | **Принято** |

**Решение.** `vitest` для раннера и юнит-тестов на чистых функциях (`lens.ts`: `getIn`/`setIn`, `format.ts`: расчёт и форматирование итогов), `@testing-library/react` — для компонентных тестов (`Toggle`, `ColorField`, пересчёт `TotalsBlock` при скрытии Discount/Taxes).

**Причина.** Vitest конфигурируется с Next.js/ESM без прослоек, в отличие от Jest. RTL — стандартный компаньон для React 19, не тянет собственной визуальной библиотеки и не противоречит ADR-002.

**Следствия.** Новые dev-зависимости: `vitest`, `@testing-library/react`, `@testing-library/jest-dom`, `jsdom`. Добавляются в `package.json` явно, версии пинятся как и весь остальной стек.

## ADR-010. Применение primary/secondary цвета в документе

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** `PLAN.md` и `UI-SPEC.md` вводят переменные `--tpl-primary`/`--tpl-secondary`, но не фиксируют, к каким именно элементам документа они применяются — при реализации это решалось бы на глаз, компонент за компонентом.

**Решение.** `primaryColor` → акцентная полоса сверху документа (`showAccentBar`). `secondaryColor` → выделение сумм Total и Balance Due в блоке итогов. Остальные элементы документа (шапка таблицы, футер) остаются нейтральными — иначе теряется контраст самого акцента.

**Причина.** Минимальный, однозначный маппинг: одна переменная — одна зона документа. Это тестируемо (компонентный тест может проверить, что `TotalsBlock` получает `--tpl-secondary`) и не требует лишних настроек «где ещё применить цвет».

## ADR-011. Формат дат: locale-маппинг вместо самописного форматтера

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** `TemplateSettings.layout.dateFormat` принимает `'us' | 'eu' | 'iso'`. Правило `CLAUDE.md` требует форматирование только через `Intl`, с явным `timeZone: 'UTC'`, без самописных хелперов. Прямого соответствия «одно значение — один `Intl.DateTimeFormat`» не было зафиксировано, а `'eu'` неоднозначен по странам (dd.mm.yyyy vs dd/mm/yyyy).

**Решение.** Маппинг на конкретные locale, каждый — валидный, поддерживаемый движком `Intl` вариант:

| `dateFormat` | `Intl.DateTimeFormat` locale | Результат |
|---|---|---|
| `'us'` | `en-US`, `{ day: '2-digit', month: '2-digit', year: 'numeric', timeZone: 'UTC' }` | `MM/DD/YYYY` |
| `'eu'` | `en-GB`, те же опции | `DD/MM/YYYY` |
| `'iso'` | `en-CA`, те же опции | `YYYY-MM-DD` |

**Причина.** `en-GB` и `en-CA` — не косметический выбор конкретной страны, а самый короткий путь получить нужный порядок частей даты через нативный `Intl` без сборки строки вручную: `en-CA` — единственная широко доступная locale, которая форматирует `2-digit` дату именно как `YYYY-MM-DD`. Все три остаются датами в UTC, интерфейс не привязывается к языку — только к порядку компонентов даты.

**Следствия.** `format.ts` экспортирует `formatDate(date, dateFormat)`, внутри — таблица `dateFormat → locale`, без ветвлений на ручную сборку строки.

## ADR-012. Save/Cancel: отдельный baseline-атом

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** `settingsAtom` — единственный источник правды, который сразу и живой черновик, и то, что автосохраняется в `localStorage`. TopBar требует индикатор «не сохранено», а Cancel обязан «вернуть к последнему сохранённому состоянию». С одним атомом это физически нечем сделать — после автосохранения черновика прежнее сохранённое состояние потеряно, сравнивать не с чем.

**Рассмотренные варианты.**

- **Позиция в `jotai-history`** — Save запоминает индекс истории, Cancel отматывает `undo()` до него, dirty = текущий индекс ≠ запомненный. Компактно, но привязывает Save/Cancel к деталям реализации `jotai-history` (программная перемотка на произвольный шаг назад, а не просто «шаг назад»).
- **Отдельный `savedSettingsAtom`** — принято.

**Решение.** Второй атом `savedSettingsAtom` (без персистентности) хранит снимок `TemplateSettings` на момент последнего Save.

```ts
export const savedSettingsAtom = atom<TemplateSettings>(DEFAULTS);

export const saveAtom = atom(null, (get, set) => {
  set(savedSettingsAtom, get(settingsAtom));
});

export const cancelAtom = atom(null, (get, set) => {
  set(settingsAtom, get(savedSettingsAtom));
});

export const isDirtyAtom = atom((get) => get(settingsAtom) !== get(savedSettingsAtom));
```

При гидрации черновика из `localStorage` (см. подводный камень ADR-3) `savedSettingsAtom` инициализируется тем же восстановленным значением — до первого Save в сессии состояние считается «сохранённым», а не «грязным».

**Причина.** Развязан от внутреннего API `jotai-history`: Save/Cancel/dirty работают через простое сравнение двух значений, что легко читать и тестировать (`ADR-9`) без знания устройства библиотеки истории. `settingsAtom !== savedSettingsAtom` — сравнение по ссылке; `fieldOf`-линзы всегда создают новый объект при записи (иммутабельный паттерн), поэтому ссылочное сравнение корректно детектирует изменение без глубокого diff.

**Следствия.** `jotai-history` продолжает версionировать только `settingsAtom` — undo/redo не знает о существовании baseline-атома и работает как раньше. Undo может пересечь точку последнего Save (откатить черновик дальше, чем в последний сохранённый момент) — это осознанно допустимо: Undo — история черновика, Cancel — откат к сохранённому, это разные операции с разной семантикой.

## ADR-013. Discount/Taxes — фиксированные демо-данные, не настройка

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** `BlockKey` в `TemplateSettings.content.show` управляет только видимостью строк «Discount»/«Taxes». Модель настроек не содержит числового поля для самой суммы скидки или ставки налога — при этом `CLAUDE.md` требует форматирование процентов через `Intl`, а откуда возникает процент в интерфейсе, было не зафиксировано.

**Решение.** Сумма скидки (`discountMinor`) и ставка налога (`taxRatePermille`) — часть демо-данных счёта в `sample-invoice.ts`, а не настраиваемого шаблона. Пользователь управляет только видимостью строк через `BlockKey`; сами величины фиксированы.

**Причина.** Задание — про настройку **шаблона** (внешний вид, состав, лейблы), а не про редактор конкретного счёта с реальными финансовыми данными. Добавление редактируемых денежных полей — рост объёма без запроса в референсе или ТЗ. Ставка налога рендерится как `Tax (8%)` через `Intl.NumberFormat(..., { style: 'percent' })` — это и закрывает требование про форматирование процентов.

**Следствия.** `sample-invoice.ts` — единственное место с этими числами; смена валюты (`ADR-014`) не пересчитывает их, только переформатирует.

## ADR-014. Валюта — формат отображения, не конвертация

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** `TemplateSettings.layout.currency: 'USD' | 'EUR' | 'PLN'` — не было зафиксировано, меняет ли переключение валюты фактические суммы (конвертация по курсу) или только то, как эти же цифры показываются.

**Решение.** Переключение валюты — чистая смена формата отображения. Суммы в минорных единицах (гроши) не пересчитываются; меняется только код валюты, передаваемый в `Intl.NumberFormat`. Locale фиксирован как `en-US` для всех валют — разделители тысяч/десятичных остаются в едином стиле, согласованном с англоязычным интерфейсом. Валютный маркер меняется вместе с кодом, но не всегда это разговорный символ: у `en-US` нет узкого глифа для PLN, поэтому `Intl` показывает ISO-код (`PLN 1,800.00`), а не «zł» — это ожидаемое следствие фиксированного locale, а не баг.

**Причина.** Реальная конвертация требует источника курсов (внешний API — недопустим по `ADR-6`, статичные курсы устареют мгновенно и создадут иллюзию точности там, где её нет). Для экрана настройки шаблона релевантен только внешний вид документа, а не бухгалтерская конвертация. Единый `en-US` locale убирает ещё одну ось несогласованности: смена валюты не должна попутно менять расстановку разделителей тысяч (`1,234.56` → `1.234,56` → `1 234,56`), это визуально не связанное с выбором валюты изменение.

**Следствия.** `format.ts`: `formatMoney(minorUnits, currency)` = `new Intl.NumberFormat('en-US', { style: 'currency', currency }).format(minorUnits / 100)`.

## ADR-015. Логотип: только через `<img src>`, никогда `dangerouslySetInnerHTML`

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Загрузка логотипа принимает SVG. SVG — не растровый формат, а XML-документ, который может содержать `<script>` и обработчики событий (`onload` и т. п.) — известный вектор XSS при загрузке пользовательских SVG.

**Решение.** Логотип (в любом формате, включая SVG) рендерится исключительно через `<img src={logoDataUrl} />` — в превью логотипа, в шапке документа, в LogoUploader. Инлайновая вставка (`dangerouslySetInnerHTML`, `<object>`, `<embed>`, `<iframe>`) для логотипа не используется никогда.

**Причина.** Браузеры не исполняют скрипты внутри SVG, загруженного через `<img>` или как CSS `background-image` — это ограничение уровня спецификации, а не библиотеки. Исполнение возможно только при инлайн-вставке разметки или загрузке через `<object>`/`<iframe>`. Ограничившись `<img>`, XSS-вектор закрывается без валидации/санитайзинга содержимого SVG (а санитайзинг SVG на клиенте — самостоятельная и не тривиальная задача, которой задание не требует).

**Следствия.** Ни один компонент не парсит содержимое загруженного файла — `FileReader.readAsDataURL` отдаёт готовую data URL, которая идёт прямо в `src`.

## ADR-016. `print-color-adjust: exact` для фоновых цветов бумаги

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Акцентная полоса (`primaryColor`) и выделение Total/Balance Due (`secondaryColor`, ADR-10) — это `background-color`. Браузеры по умолчанию не печатают фоновые цвета (экономия чернил); без явного указания это уберёт весь смысл настройки брендинга именно там, где он должен быть виден офлайн — на распечатанном или сохранённом в PDF счёте.

**Решение.** В `InvoicePaper.module.css` на корневом элементе бумаги: `print-color-adjust: exact; -webkit-print-color-adjust: exact;` — покрывает все фоновые цвета внутри, включая акцентную полосу и итоги.

**Причина.** Единственная альтернатива — оставить как есть и потерять брендинг при печати, что прямо противоречит цели экрана. Никаких трейд-оффов у этого свойства нет: оно не влияет на экранное отображение, только на печать/PDF.

## ADR-017. `ink-subtle` только для placeholder — остальное на `ink-muted`

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** При a11y-прогоне на этапе полировки посчитан реальный контраст токенов `UI-SPEC.md`: `--ink-subtle` (`#949aa6` на light, `#6d7380` на dark) даёт **2.78:1** и **3.62:1** к `--surface` — ниже требования 4.5:1 из чеклиста того же документа («Доступность» → «Контраст текста не ниже 4.5:1 в обеих темах»). Токену при этом назначены не только плейсхолдеры, но и подсказки/ошибки под полями и счётчики символов textarea — то есть реальный, читаемый контент, а не декоративный текст.

**Решение.** Разделяем по ролям:

- **`ink-subtle` остаётся только для `placeholder:`** — placeholder не является персистентным контентом (исчезает при вводе), это общепринятое исключение из требования контраста для основного текста.
- **Подсказки/ошибки под полями (`Field`), счётчик символов (`TextArea`), индикатор «Not saved» (`TopBar`) — переведены на `ink-muted`**, который проходит 4.5:1 в обеих темах (5.27:1 light, 6.54:1 dark).
- Декоративные иконки (например, `ChevronDown` в `Select`) не считаются текстом и не пересматриваются — они избыточны по отношению к другим сигналам состояния контрола.

**Причина.** Альтернатива «зафиксировать сам токен `ink-subtle` темнее/светлее, чтобы прошёл 4.5:1 везде» была отклонена: подходящие значения (`#6b7280` light, `#7d8390` dark) визуально почти совпадают с `ink-muted`, что стирает трёхуровневую иерархию текста (`ink` / `ink-muted` / `ink-subtle`), заложенную в токенах. Разделение по ролям сохраняет иерархию там, где контраст не критичен (плейсхолдер), и чинит его там, где текст реально нужно прочитать.

**Следствия.** `UI-SPEC.md` обновлён: строка токена `--ink-subtle` и строка типографики «Подсказка, ошибка» отражают новое разделение ролей.

## ADR-018. Тема — cookie + SSR вместо localStorage

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** Тема хранилась в `localStorage` (`atomWithStorage`). Блокирующий `<script>` в `app/layout.tsx` патчил `data-theme` на `<html>` до первой отрисовки, закрывая CSS-мигание, но `themeAtom` в React стартовал с дефолта `'light'` до эффекта после монтирования — иконка Sun/Moon в `TopBar` на долю секунды показывала неверное состояние даже когда фон уже был верным.

**Решение.** Тема переезжает на cookie (`its-theme`, см. `lib/theme-cookie.ts`). `app/layout.tsx` — `async` Server Component, читает cookie через `cookies()` из `next/headers` и рендерит `<html data-theme={theme}>` с верным значением сразу. Новый клиентский компонент `ThemeHydrator` вызывает `useHydrateAtoms([[themeAtom, theme]])`, так что React получает верное значение уже на первом рендере, а не после эффекта. Блокирующий `<script>` удалён — не нужен, сервер уже отдаёт верный HTML.

**Причина.** Тема — единственный кандидат на настоящий SSR из всего persisted-состояния студии: значение маленькое (`'light' | 'dark'`), cookie отправляется с каждым запросом и читается на сервере без ограничений размера, которые исключают такой подход для черновика настроек (см. ADR-19).

**Следствия.** `useHydrateAtoms` здесь не нарушает правило `CLAUDE.md` про `localStorage`: значение приходит из HTTP-заголовка cookie, прочитанного на сервере, а не из `window`/`localStorage` во время клиентского рендера — это принципиально другой источник данных. Существующий эффект в `TopBar`, синкающий `data-theme` при переключении, дополнительно пишет cookie через `setThemeCookie`, чтобы следующая перезагрузка тоже была верной. Чтение cookie в `app/layout.tsx` переводит весь роут `/` из статического рендера в динамический per-request (подтверждено выводом `pnpm build`: роут `/` помечен как `ƒ` (Dynamic), а не `○` (Static)) — ожидаемое и приемлемое следствие для текущей цели хостинга, но это реальный архитектурный сдвиг по сравнению с полностью статическим приложением до этой задачи, и его стоит иметь в виду, если для этого роута когда-нибудь понадобится статический экспорт или ISR.

## ADR-019. Гидратация черновика — skeleton, не ускорение через `useHydrateAtoms`

**Статус:** принято · **Дата:** 2026-09-15

**Контекст.** В отличие от темы (ADR-18), черновик настроек (имя, логотип, цвета, контент) не может стать по-настоящему SSR — в проекте нет бэкенда, а cookie не подходит из-за лимита ~4Кб и потенциально большого base64-логотипа. До гидратации (эффект после монтирования, ADR-3) все компоненты, читающие `settingsAtom`, показывали `DEFAULTS` как будто это настоящие данные пользователя.

**Рассмотренные варианты.**

- **Подход A (отклонён)** — тот же приём, что и для темы: блокирующий `<script>` синхронно читает `localStorage.getItem('its:draft')` до отрисовки, React подхватывает значение через `useHydrateAtoms` на первом рендере. Максимально быстро, но это чтение `localStorage`, привязанное к рендеру — впритык к правилу `CLAUDE.md` «черновик читается только в эффекте», требует отдельного документированного исключения.
- **Подход B (принят)** — гидратация остаётся полностью в эффекте, без изменений механизма. Вместо показа `DEFAULTS` как настоящих данных — нейтральный skeleton (`StudioSkeleton`) на всё время эффекта.

**Решение.** Подход B. Новый `isHydratedAtom` (`lib/atoms/saved.ts`) и `HydrationGate` (перенимает эффект гидратации у `TopBar`) гейтят всю студию: пока `isHydratedAtom` — `false`, показывается `StudioSkeleton`, повторяющий размеры реального макета.

**Причина.** Пользователь явно предпочёл остаться в рамках правила про `localStorage`, а не вводить исключение ради скорости. Задача была не «мигание должно быть быстрее», а «дефолты не должны показываться как настоящие данные» — skeleton закрывает именно это, не трогая механизм гидратации.

**Следствия.** Три состояния черновика, не два: загрузка (skeleton) → черновик найден (реальные значения) или черновика нет (`DEFAULTS` как осознанный финальный результат). Окно ожидания не стало короче технически, но пользователь никогда не видит чужие/неправильные данные.
